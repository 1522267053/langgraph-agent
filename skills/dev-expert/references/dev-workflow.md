# 人机协作开发流程（dev-workflow）

> 需求 → 开发 → 测试 → 闭环 的六阶段协作规范。适用于「开发者（人）+ Dev Agent + QA Agent」三方协作的软件项目。
>
> 模板（台账列定义 / AGENTS.md 骨架 / 详设骨架 / 实测报告骨架 / 教训回写格式）见 [collaboration-templates.md](collaboration-templates.md)。
>
> 本文件是**跨项目通用流程**的唯一真源；项目 `AGENTS.md` 只放项目特有的落位路径与枚举值，不复制流程正文。
>
> 全部规律取自真实项目实证：elink-monitor（企业交付，267 笔提交 / 100 条需求台账 / 49 篇 docs / AGENTS.md 835 行 53 次修订 / 18 个 Wave）+ langgraph-agent（个人单源，529 笔提交 / AGENTS.md 272→332 行 25 次修订）。

## 核心权责线

> **Agent 的自主权止于「工作区改动 + 验证证据」，版本库主权与需求裁决权在人。**

| 角色 | 承担者 | 职责 | 绝对边界 |
|------|--------|------|---------|
| **需求方** | 产品 / 领导 / 用户 / 测试 / 开发 | 提出原始诉求（口语化） | 不写方案 |
| **开发者（人）** | — | 理解需求、登记台账、排期、方案拍板、**git commit / push** | 不手写重复代码 |
| **PM** | 人兼任，或独立 PM Agent | 派单、拼任务描述（含工作目录/文件清单/验证要求）、裁决口径争议 | — |
| **Dev Agent** | dev-expert 技能 | 读规则 → 改码 → 自验 → 汇报 | **不得 commit / push**；不得直接联系 QA |
| **QA Agent** | test-expert 技能 | 真机实测 → 缺陷分级 → 三态结论 | **不得改代码**；环境不足必须出 BLOCKER 而非「不通过」 |

**协作链路**：QA 不通过 → 反馈给 PM/人 → 人让 Dev 返工 → Dev 按缺陷清单修改 → 通知人重新派 QA。**Dev 不直接联系 QA。**

## 六阶段主流程

```
S0 立项定规则（项目级，一次性 + 持续加厚）
        ↓
S1 需求登记（人）→ S2 方案设计（人拍板）→ S3 开发执行（Dev Agent）
        ↑                                          ↓
        │                                          ↓
        └———— S5 闭环沉淀 ←———— S4 测试验证（QA Agent）
              （人授权提交）           ↓ 不通过
                                 回 S3 返工
```

| 阶段 | 执行者 | 一句话 |
|------|--------|-------|
| S0 | 人（可与 Agent 讨论） | 定 AGENTS.md 规则，一次性 + 每次事故后加厚 |
| S1 | **人** | 需求结构化登记 + 排期（个人项目可省略） |
| S2 | Agent 起草 → **人拍板** | 详设 + Wave 拆分 + **测试用例先行** |
| S3 | Dev Agent | 8 步执行，改动留工作区 |
| S4 | QA Agent | 真机实测，三态结论，未修复项强制披露 |
| S5 | Agent 起草 → **人授权提交** | 教训回写 AGENTS.md + 台账 + 索引 + memory + commit |

## S0 立项定规则

| 项 | 内容 |
|----|------|
| **触发** | 新项目启动；或现有 AGENTS.md 缺失关键章节 |
| **执行者** | 人主导，可与 Agent 讨论制定 |
| **动作** | 建 AGENTS.md 初始骨架，**只需 ~100 行覆盖 7 小节** |
| **产物** | `AGENTS.md`（前端项目另建 `frontend/AGENTS.md`） |
| **门禁** | Agent 冷启动只读 AGENTS.md 能答出：怎么跑起来、代码放哪、什么禁止 |

**7 小节**：①项目概述（技术栈）②构建与运行命令 ③端口规则 ④项目结构树 ⑤核心架构（数据流图）⑥数据库（表清单 + 建模红线）⑦编码注意事项

→ 骨架模板见 [collaboration-templates.md · T2](collaboration-templates.md#t2-agentsmd-初始骨架)

**S0 的两条后续纪律**：
1. **第 4 天做一次全量规范自查**（实证：elink 首提交后第 4 天即 `refactor: 全量修复AGENTS.md编码规范违规项`）
2. **规则文件要主动瘦身**（实证：langgraph-agent 曾 -514 行精简）。判据：**规则是否需要「同时生效」**——安全红线/架构约定/唯一真源留下，操作手册类外移。超 450 行必须外移。

## S1 需求登记

| 项 | 内容 |
|----|------|
| **触发** | 任何来源的新诉求 |
| **执行者** | **人**（理解 + 结构化 + 排期）。Agent 不代劳 |
| **动作** | 写台账一行；排期 |
| **产物** | 企业项目：`docs/01-需求/*.xlsx`（唯一需求源）<br>个人项目：**省略台账** |
| **门禁** | 类型落 4 值 / 状态落 5 值 / 带`【标题】`前缀 / 计划起止已填 / 枚举冲突已在备注说明 |

**启用判据只有一条**：需求是否来自开发者之外、是否需要向别人交代。

**三条硬规则**：① 枚举必须收敛，冲突时显式记录不私自扩枚举 ② `【标题】`前缀是检索锚点 ③ 状态只在一处维护

**排期必须双轨**（交付周期双峰：中位 0 天、当日完成 52%、p90 15 天、max 38 天）：
- 快速通道（单文件/口径明确）：S1 → S3 → S5
- 完整流程（≥3 文件/跨模块/动数据模型）：S1 → S2 → S3 → S4 → S5

→ 台账 14 列定义见 [collaboration-templates.md · T1](collaboration-templates.md#t1-需求台账列定义)

**需求描述天然口语化，不要指望它精确**（实证：中位 56 字、21 条 < 30 字）。降熵发生在 S2，不在 S1。

## S2 方案设计

| 项 | 内容 |
|----|------|
| **触发** | 需求进入排期；或改动 ≥3 文件 / 跨模块 / 动数据模型 |
| **执行者** | Agent 起草 → **人拍板**（口径争议由人裁决） |
| **动作** | ①写详细设计 ②拆 Wave ③**测试用例先行** |
| **产物** | `docs/03-详细设计/<主题>.md`、`docs/04-测试内容/<主题>测试文档.md`；大需求另加 `docs/02-总体计划/` |
| **门禁** | 详设含数据模型/时序图/模块清单/上线检查清单/**已知边界**；用例有编号 + 可判定的预期结果；口径争议已由人裁决并记入 `memory(decision)` |

**关键点**：
- **测试用例先行**——S2 就写 `docs/04-测试内容`，不是 S4 才补。用例编号（`SCAN-001`）在 S4 被 QA 直接复用。
- **Wave 拆分是 S3 能小步验证的前提**（实证：连续 13 个 Wave 编号，每 Wave 一套断言脚本）。按天/按能力切，每 Wave 独立可验证，**诚实标注完整度**（完整/简化/骨架）。
- **详设必须写「已知边界」**——明确"本期不实施"的部分与未来触发条件。

⚠️ **详设可能滞后于最新决策**：动手前以「任务书字段规格 + AGENTS.md」为准，差异在汇报中显式声明。

→ 详设骨架见 [collaboration-templates.md · T3](collaboration-templates.md#t3-详细设计文档骨架)

## S3 开发执行

| 项 | 内容 |
|----|------|
| **触发** | PM/人下发任务（含工作目录、需求序号、验收口径） |
| **执行者** | Dev Agent |
| **产物** | 代码改动（**留工作区，不 commit**）+ `temp/_check_waveN_*.py` 断言脚本 + 开发报告 |
| **门禁** | 每步有证据；**无证据 = 未完成** |

### 8 步执行序列

```
1. load_skill("dev-expert") → 按路由表识别任务类型 → 加载对应 reference
2. 通读 AGENTS.md 全文（含唯一真源清单、红线约束）
3. memory_search 检索项目历史决策/教训/口径（避免重复踩坑）
4. todowrite 拆 3-7 个子任务
5. 读懂现状再动手（禁止瞎猜）
6. 改码：局部补丁，禁止无必要全文重写；同一文件禁止并行编辑（会互相覆盖）
7. 自验：写 temp/_check_waveN_*.py 断言脚本 + 跑 lint/format/构建
8. 汇报：改动文件清单 + 验证证据（命令/退出码/关键输出）+ 已知限制 + 未验证项
```

### S3 出口门禁

☐ 已通读 AGENTS.md ☐ 已 `memory_search` 历史教训 ☐ 未引入第二份逻辑（唯一真源已复用）☐ 权限/安全边界在**代码里**不在提示词里 ☐ lint/format 通过且不高于基线告警数 ☐ 断言脚本全绿 ☐ 造数复制自**真实文件** ☐ 验证脚本未碰生产库 ☐ **未 commit**

### 两条硬纪律（违反即 P0，均有真实事故）

**① 确定性归代码，语义性归 LLM**

新增决策点先问：「这是确定性的（→流程/代码）还是语义性的（→Agent）？」

| 决策类型 | 归属 | 机制 |
|---------|------|------|
| 权限校验、群聊/上下文判定、白名单、外发动作、索引名一致性 | **代码** | 硬编码校验函数 |
| 调用哪个工具、传什么参数、是否需人工确认、语义归类 | **LLM** | ReAct 决策 |

> 事故实证：合并打包工具只有「chat_id 非空」+「任务属本群」两道闸门，**都不校验操作人** —— 同群任何成员说「汇总一下进度」即可触发打包发群 + @发起人 + 刷 26 条未交局名单，属**越权取数/骚扰且无审计**；而提示词里只写了「发起人说这句话必须传 force=true」，等于把确定性安全边界交给 LLM 语义判断。
>
> **通用纪律：权限边界必须落在工具代码里，严禁只写在提示词让 LLM 自觉；同一校验禁止两处实现。**

同类：需 @ 某人必须代码侧直发（回复队列无 mention 字段，委托 LLM 转述必然失败）。

**② 测试造数必须复制生产真实结构**

> 事故实证（两次实锤）：造数用「用户编号/省份/地市/区县」列序，生产实际是「省份/地市/区县/供电所/用户编号」→ 写死 `index=3` 命中「供电所」→ 真实文件 `actual_rows=0`。**整套基线全绿，真实数据必挂。**

规律：① 造数优先复制真实文件/表头而非手写；② 对依赖外部格式契约的代码，加「同一语义多形式」参数化断言（如列序无关双样本）；③ **测试全绿 ≠ 正确，真实样本才是最终判据**。

> 配套事故：验证脚本 `import` 生产 engine 造数 → 污染生产库（残留 `R:LEAKTEST` 脏数据，需备份后按 id 精确删除）。
> **纪律：验证脚本涉及 DB 写入时，第一行就建临时库（`tempfile` + `create_async_engine`），绝不 import 生产 engine；跑完先查生产库计数再继续。**

### 唯一真源纪律

**Agent 最常犯的错不是写错逻辑，而是复制一份逻辑。** 改任何判定/校验/口径前，先定位唯一真源并复用；发现第二份实现即视为缺陷。项目应在 AGENTS.md 维护《唯一真源清单》索引表（格式见 [collaboration-templates.md · T5](collaboration-templates.md#t5-教训回写条目格式)）。

## S4 测试验证

| 项 | 内容 |
|----|------|
| **触发** | Dev Agent 汇报「已就绪」 |
| **执行者** | QA Agent（test-expert） |
| **动作** | 环境自检 → 按 `docs/04-测试内容` 真机实测 → 缺陷分级 |
| **产物** | `docs/05-测试结果/<主题>-YYYY-MM-DD-测试报告.md` |
| **门禁** | 三态结论明确；未修复项强制披露；未改任何代码 |

### 返工是设计特性，不是失败

| 指标 | 企业项目实证 | 个人项目实证 |
|------|------------|------------|
| `feat` 后紧接 `fix` | 28/73 = **38%** | 64/145 = **44%** |
| `fix` 占全部提交 | 118/267 = **44%** | 264/529 = **50%** |

原因：需求锚定**真实世界的物理契约**（真实 xlsx 表头顺序、真实群成员名单、真实报文嵌套层数、真实国产化 OS 环境、真实浏览器 CDP 行为、真实模型网关超时），写代码时无法预知。

**因此 S3→S4→S3 的循环是常态，不要把它当失败，也不要为了"一次通过"而降低实测强度。**

### 三态结论

| 结论 | 判据 |
|------|------|
| ✅ **通过** | 审查项全满足 + 所有测试实跑通过 + 覆盖率达验收口径 |
| ❌ **不通过** | 附缺陷清单（编号 / 文件:行号 / 描述 / 建议 / P0-P2 级别） |
| ⛔ **BLOCKED** | 环境能力不足，必须输出 BLOCKER 区块（capability / reason / need_from_human / fallback_options） |

> **不得用「不通过」代替 BLOCKER**——环境不足必须上报，否则人会误以为是代码问题而白返工。

### 缺陷分级

- **P0**：阻塞核心功能 / 数据丢失损坏 / 安全漏洞（注入、越权、敏感信息泄露）→ 禁止合并
- **P1**：核心功能可用但有缺陷 / 严重性能问题 / 缺关键路径测试 → 修复后再合并
- **P2**：边界问题 / 文案错误 / 非关键路径 → 后续迭代

### 报告必须能「打脸自己」

> 实证原文：*"历史测试结果：30 个用例全部 PASS，发现 8 个 BUG"* —— **全 PASS 与发现 8 个 BUG 并存**
> *"当前修复状态：8 个 BUG 中 5 个已修复，2 个无需修改，1 个被澄清为非 BUG"*

**报告的价值在于如实记录未修复项，不是证明成功。** 结论允许且应当写「❌ 不通过」。

→ 报告骨架、BLOCKER 格式、验证三件套见 [collaboration-templates.md · T4](collaboration-templates.md#t4-真机实测报告骨架)

## S5 闭环沉淀

**这是最容易被跳过、却最能放大价值的一环。没有 S5，同一个坑会踩第二次。**

| 项 | 内容 |
|----|------|
| **触发** | S4 出结论后（**无论通过与否**） |
| **执行者** | Agent 起草全部产物 → **人审阅 → 明确说「提交」才 commit** |

### 5 件事

**① 教训回写 AGENTS.md（最重要）**

回写判据：排查 ≥40 分钟 / 静态全绿但实跑翻车 / 第三方库隐式行为 / 安全权限数据边界类 → **必须**回写；一次性笔误 → 不回写。

固定格式：
```markdown
- **<结论式纪律，一句话可执行>**（YYYY-MM-DD 实测修复[, 任务#N 复现]）：
  原实现是 <X> → 真实现象是 <Y> → 根因是 <Z> → 修复口径是 <W>。
  **通用纪律：凡<同类场景>一律<正确做法>，禁止<错误做法>**
```

格式要点：结论前置加粗 / 必带日期 + 「实测」字样 / 保留现象与根因（只有结论没根因，换场景就不会迁移）/ 以「通用纪律」收尾（从个案抽象到同类，这是回写的真正目的）。

**② 需求台账状态更新**（企业项目）
`开发中 → 已完成` + 实际完成时间。可单独成笔，但 subject 必须写明需求序号与状态：
`docs: 更新需求台账（#95 稽查小e 完成 / #99 第三方 WS 开发中）`

**③ 文档索引同步**
`docs/文档索引.md` 记录路径 + 需求提出时间 + 用途说明。移动/重命名文档后同步更新其他文档中的路径引用。
> 实证：文档索引被 **40 笔**提交触及，比 AGENTS.md 的 38 笔还多——索引是活的目录，不是摆设。

**④ memory 沉淀**

| category | importance | tier | 用途 |
|----------|-----------|------|------|
| `decision` | 5 | hot | 关键技术决策 + **撤销条件** |
| `lesson` | 4-5 | hot/warm | 新 Bug 模式、兼容性陷阱 |
| `knowledge` | 4 | warm | 新规范、唯一真源、口径 |
| `event` | 2-3 | cold/warm | 写后即记（改了什么/验证结果/是否 commit） |
| `task` | 5 | hot | **Handoff**（长任务中断续做） |

> **未 commit 的改动必须在记忆标题标注「（未commit）」**——跨会话 handoff 的关键。

**⑤ 提交（人授权后执行）**

Conventional Commits，subject 必须具体到「不看 diff 也懂」，最好带现象或根因：
- ✅ `fix: 区县列/对齐键改为按表头名解析（真实文件 actual_rows=0 P0）`
- ✅ `fix: 责任人来源改为群级身份表（原用全体群成员，误 @ 11 人 / 进度虚报 12）`
- ❌ `fix:修改代码` / `docs:更新文档`（无信息量 + 冒号后无空格）

**文档与代码同笔提交**：代码改动若产生新口径/新纪律，AGENTS.md 与代码同笔（实证 34 笔为此模式）。

### ⚠️ 规则文件里写了什么，Agent 就遵守什么；没写的立刻退化

**铁证**（同一开发者、同一 Agent、同一时期，唯一变量是「规则文件里有没有写」）：

| | 有《Git 提交规范（强制）》整章 | 无该章节 |
|---|---|---|
| 项目 | langgraph-agent | elink-monitor |
| 冒号后无空格的提交 | 67 笔 / 529（13%） | **123 笔 / 267（46%）** |
| 无信息量提交 | 6 笔 | `fix:修改代码` + `docx:修跟更新文档`（type 拼错） |

→ **规则必须逐条可检查**：写「提交信息要清晰」无效，写「冒号后有且仅有一个空格 + 禁止'修改代码'字样 + type 不得拼错」才有效。

### 共通文件拆笔技术

因要求文档与代码同笔，AGENTS.md 成了多主题共通文件，非交互环境 `git add -p` 不可用：

```
脚本解析 git diff -U3 的 hunk → 按关键词分类主题
→ 从 HEAD 版重建「仅主题A」的中间文件 → 覆盖 + git add
→ 立即用备份恢复完整工作区版
关键自检：重建「HEAD + 全部 hunk」必须逐字等于完整工作区版（断言 True），否则拆分逻辑有误
```
> 实证效果：一笔得 WS 主题 20 行，另一笔得归档主题 19+1 行，归属完全正确。

## 四层文档落位规则

| 层 | 载体 | 回答什么 | Agent 是否自动加载 |
|----|------|---------|------------------|
| **① 宪法层** | `AGENTS.md`（+ `frontend/AGENTS.md`） | 改代码必须遵守什么、唯一真源在哪、什么绝对禁止、**开发流程本身** | ✅ **是**（提示词强制通读） |
| **② 台账层** | `docs/01-需求/*.xlsx` + `docs/文档索引.md` | 谁在什么时候提了什么、现在什么状态 | ❌ 需主动查 |
| **③ 方案层** | `docs/02-总体计划`、`03-详细设计`、`04-测试内容`、`05-测试结果`、`06-使用指南` | 怎么设计、怎么测、测出什么 | ❌ 需主动查 |
| **④ 记忆层** | memory（热/温/冷） | 跨会话状态、口径决策、未 commit 的进行时 | ✅ 索引自动注入 + `memory_search` |

### 关键结论：流程规范必须写进 AGENTS.md，不能只放 docs/

Dev Agent 的提示词通常只强制读 `README.md / AGENTS.md / CLAUDE.md` 三个文件；**放 `docs/` 里 Agent 不会主动找，规范就等于不存在**。

因此：
- **AGENTS.md 放**：流程骨架（六阶段总表 + 门禁清单）+ 项目特有的落位路径与枚举值 + 教训纪律条目 + 唯一真源清单
- **docs/ 或技能 references 放**：详细模板、完整说明、历史设计
- 两边**互相链接不复制**（information 只放一处）

### docs/ 六分类目录规则

```
docs/
├── 文档索引.md          ← 必须同步记录路径 + 需求提出时间 + 用途
├── 01-需求/             ← 平台能力、外部依赖、需求台账（唯一需求源）
├── 02-总体计划/         ← 功能总览、总体设计、阶段计划
├── 03-详细设计/         ← 模块、权限、插件、迭代设计
├── 04-测试内容/         ← 测试方案、环境、用例
├── 05-测试结果/         ← 测试结果、Bug 清单、回归记录
└── 06-使用指南/         ← 用户和运维使用配置说明
```

- 新文档必须放入对应分类目录，**不直接放 `docs/` 根目录**
- **不创建按日期划分的目录**；日期写在 Markdown 顶部（`需求提出时间` + `时间依据：文件最后修改时间`）
- 二进制文档（`.docx`）无法加元信息，日期只登记在 `文档索引.md`
- 过期文档**标「历史快照」而非删除**，顶部链接最新设计

## 项目类型裁剪

**判据只有一条：需求是否来自你之外、是否需要向别人交代。**

| 阶段 | 企业交付项目 | 个人/单源项目 |
|------|------------|--------------|
| S0 规则 | AGENTS.md 厚规则（业务口径复杂需一次读全） | AGENTS.md 薄索引 + 细节外移 |
| S1 台账 | **必须** xlsx 14 列 | **省略**（但要在 AGENTS.md 显式写明"本项目需求单源，省略台账"，否则 Agent 会照企业规则去找台账） |
| S2 详设 | 必须（需向测试/运维/领导交代） | 按需（复杂功能才写） |

| S4 测试 | 真机实测报告 + 缺陷编号台账 | 断言脚本 + 提交信息写明验证结论 |
| S5 沉淀 | AGENTS.md 纪律回写 + 台账 + 索引 + memory | AGENTS.md 纪律回写 + memory |

> **反面教训**：给个人项目套企业流程 → 产生空文档；给企业项目省台账 → 三个月后无人记得需求为什么这么定。

## 反模式清单

每条均有真实事故，命中即复用正确判据（对齐 `error-ledger`）。

| 反模式 | 后果 |
|--------|------|
| 造数手写而非复制真实文件 | 基线全绿掩盖 P0（`actual_rows=0`） |
| 验证脚本 import 生产 engine 造数 | 污染生产库（残留测试脏数据） |
| 权限边界只写提示词 | 越权群发 + 无审计 |
| 群发文案硬编码「已全部收齐」 | 与未交局告警自相矛盾，误导用户 |
| 文件名 verbatim 匹配识别类型 | 真实业务名不命中，能力有却没用上 |
| session 逃出 `async with` 继续用 | **静默**连接泄漏（`close()` 后 `_connection` 不置 None，不报错） |
| 写死列号 / 写死时区副本 | 表头顺序一变即写错列、覆盖人工数据；国产化 OS 无 zoneinfo 键库直接启动崩溃 |
| 按滞后的详设实现 | 字段口径返工 → **以任务书 + AGENTS.md 为准** |
| 并行编辑同一文件 | 互相覆盖 |
| 委托 LLM 转述「@某人」 | 回复队列无 mention 字段，用户未被 @ |
| 显式传参与 `**kwargs` 同名键冲突 | `duplicate kwarg` 整条链路挂；`dict.get(fallback)` 的 fallback 会先求值 |
| Agent 自行 commit | 越权，版本库主权在人 |
| 环境不足给「不通过」而非 BLOCKER | 人误判为代码问题，白返工 |
| 把流程规范只写在 docs/ | Agent 不主动读，规范等于不存在 |
| 规则写成「良好愿望」而非可检查断言 | Agent 直接退化（提交规范缺失 → 46% 格式违规） |
