## T1 需求台账列定义

**适用判据（只有一条）**：需求是否来自开发者之外、是否需要向别人交代。

| 项目类型 | 是否启用台账 | 理由 |
|---------|------------|------|
| 企业交付（需求来源 ≥2 类） | **必须** | 口头需求会失忆、会变更、需追责 |
| 个人/单源项目 | **省略** | 需求在脑子里，写台账是空转；状态由 git 历史 + memory 承载 |

> 实证：elink-monitor 需求来源分布 产品 26 / 领导 26 / 用户 23 / 测试 16 / 开发 9 —— **74% 来自开发者之外**，故必须台账。langgraph-agent 需求 100% 来自本人，故无台账（0 笔提交触及）。

### 落位

```
docs/01-需求/<项目名>需求池管理表.xlsx    ← 唯一需求源
```

**禁止**再维护独立的需求 Markdown 清单（会出现两处状态不一致）。

### Sheet 结构（三 Sheet）

| Sheet | 内容 |
|-------|------|
| `Sheet1` | 需求池主表（**表头在第 9 行**，前 8 行留标题/说明区） |
| `辅助列` | 按平台/模块/类型/来源/优先级/状态的数量统计 |
| `历史功能` | 旧系统功能迁移清单（如有） |

### 主表 14 列

| # | 列名 | 填写规则 |
|---|------|---------|
| 1 | 序号 | 递增整数，**提交信息与测试用例编号都引用它** |
| 2 | 提出日期 | `YYYY-MM-DD`；无法确定时填 `/` |
| 3 | 需求平台 | 产品形态枚举（如 `全部`/`公共版`/`个人版`/`稽查版`） |
| 4 | 功能模块 | 模块枚举（如 `日程管理`/`工作总结`/`系统级`） |
| 5 | 需求类型 | **只允许 4 值**：`BUG` / `功能优化` / `体验优化` / `新增功能` |
| 6 | 需求描述 | **必须以 `【标题】` 前缀开头**，后接口语化描述 |
| 7 | 需求来源 | 枚举：`产品` / `领导` / `用户` / `测试` / `开发` |
| 8 | 优先级 | `高` / `中` / `低` |
| 9 | 需求状态 | **只允许 5 值**：`待排期` / `开发中` / `已完成` / `暂停` / `拒绝` |
| 10 | 计划开始时间 | 排期结果 |
| 11 | 计划完成时间 | 排期结果 |
| 12 | 实际完成时间 | S5 回填 |
| 13 | 备注 | 依赖关系、枚举冲突说明、拒绝/暂停原因 |

### 三条硬规则

1. **枚举必须收敛**，且**冲突时显式记录、不私自扩枚举**。
   > 实证范例（需求 #93 备注原文）：*"原计划'重构'不在枚举内，调整为'新增功能'并在描述中说明含 work_attachment 迁移改造"*
2. **`【标题】` 前缀是检索锚点**，不是格式美化。它让提交信息、测试用例编号、AGENTS.md 纪律条目都能反查到需求序号。
   > 实证：100 条需求中 72 条采用（`【日程数据隔离】`、`【时间幻觉】`、`【风险问题整改智能催办与汇总】`）
3. **状态只在一处维护**。Markdown 文档负责背景/设计/测试，**不重复维护需求状态**。

### 排期必须双轨（交付周期双峰分布）

> 实证 n=85：中位 **0 天** | 当日完成 **52%** | 均值 3.7 天 | p90 15 天 | max 38 天

| 轨道 | 判据 | 走哪些阶段 |
|------|------|-----------|
| 快速通道 | 单文件 / 口径明确 / 无数据模型变更 | S1 → S3 → S5 |
| 完整流程 | ≥3 文件 / 跨模块 / 动数据模型 / 新业务链路 | S1 → S2 → S3 → S4 → S5（大需求拆 Wave） |

**禁止假设统一迭代节奏**——52% 的需求当天提当天完，长尾是 38 天战役，两者不能用同一套排期。

### S0 的两条后续纪律（实证有效）

1. **第 4 天做一次全量自查**
   > 实证：elink-monitor 2026-06-15（首提交后第 4 天）`refactor: 全量修复AGENTS.md编码规范违规项 + 前端适配新模板`
   > 初始规则一定有不一致，早收敛比晚收敛便宜。
2. **规则文件要主动瘦身**
   > 实证：langgraph-agent 2026-06-25 `docs: 精简 AGENTS.md`（**-514 行**，557→154），细节外移到 `skills/*/references/`
   > **判据：规则是否需要「同时生效」**——安全红线 / 架构约定 / 唯一真源必须留在 AGENTS.md 一次读全；操作手册类外移。
   > 阈值建议：超过 450 行必须外移，本文件只留索引链接。

### 两种收敛策略（都对，按业务复杂度选）

| 策略 | 适用 | 实证 |
|------|------|------|
| **单文件厚规则** | 业务口径复杂、需一次读全（多产品形态、多外部契约） | elink-monitor 835 行，含 26 行"禁止"、30 行"必须"、15 行"口径" |
| **薄索引 + 分层 references** | 规则可分域、按需加载 | langgraph-agent 272→332 行 + `skills/*/references/` 7 个技能分域 |

### 报告必须能「打脸自己」

> 实证（`工作总结测试BUG清单.md` 头部原文）：
> *"历史测试结果：30 个用例全部 PASS，发现 8 个 BUG"* —— **全 PASS 与发现 8 个 BUG 并存**
> *"当前修复状态：8 个 BUG 中 5 个已修复，2 个无需修改，1 个被澄清为非 BUG"*

**报告的价值在于如实记录未修复项，不是证明成功。** 结论允许且应当写「❌ 不通过」。

### 三态结论（QA Agent 强制）

| 结论 | 判据 |
|------|------|
| ✅ **通过** | 审查项全满足 + 所有测试实跑通过 + 覆盖率达验收口径 |
| ❌ **不通过** | 附缺陷清单（编号 / 文件:行号 / 描述 / 建议 / P0-P2 级别） |
| ⛔ **BLOCKED** | 环境能力不足，必须输出 BLOCKER 区块 |

**BLOCKER 区块格式**（供上游正则解析）：

```
BLOCKER:
- capability: <缺什么能力，简短英文标签，如 network_access / playwright_browser / elink_desktop_client>
- reason: <为什么缺，1-2 句>
- need_from_human: <需要人类提供什么才能继续>
- fallback_options:
  - <可降级方案 1>
  - <可降级方案 2>
```

> **不得用「不通过」代替 BLOCKER**——环境不足必须上报，否则人会误以为是代码问题而白返工。

### 缺陷分级

| 级别 | 判据 | 处置 |
|------|------|------|
| **P0** | 阻塞核心功能 / 数据丢失损坏 / 安全漏洞（注入、越权、敏感信息泄露） | 禁止合并 |
| **P1** | 核心功能可用但有缺陷 / 严重性能问题 / 缺关键路径测试 | 修复后再合并 |
| **P2** | 边界问题 / 文案错误 / 非关键路径 | 后续迭代 |

### 无单测框架项目的「验证三件套」

两项目 AGENTS.md 都明写"无测试框架，修改后请运行 ruff check + ruff format"，但**实际验证强度远超 lint**：

| 形态 | 位置 | 作用 |
|------|------|------|
| **a) 一次性断言脚本** | `temp/_check_wave<N>_<主题>.py` | 每 Wave 一套，跑完留档可复跑（实证：elink `temp/` 84 个文件） |
| **b) 真机实测报告** | `docs/05-测试结果/*.md` | 带 msg_id / DB 落库 / 日志行号 / 修复前后 JSON 对比 |
| **c) 缺陷编号台账** | 同上 | `BUG-011~039` / `P0-1` / `REG-005`，QA 与 Dev 共用编号流转 |

**临时脚本落位规则**：
- 优先项目内 `temp/` 或 `workspace/temp/`，文件名 `_check_` / `_verify_` / `_tmp_` 前缀
- 禁止写系统盘根目录、禁止污染源码目录
- ⚠️ 特例：某些项目 `temp/` 是运行时数据目录（存真实 token/credentials），此时改用 `workspace/temp/` 或 `%TEMP%` 子目录

## T5 教训回写条目格式

**这是整个流程的价值放大器。没有 S5 回写，同一个坑会踩第二次。**

### 回写判据

| 情况 | 是否回写 AGENTS.md |
|------|------------------|
| 排查耗时 ≥40 分钟 | **必须** |
| 「静态检查全绿但真机翻车」 | **必须** |
| 第三方库/协议的隐式行为 | **必须** |
| 安全/权限/数据边界类 | **必须**（标为红线） |
| 一次性笔误 | 不回写（避免文件膨胀） |

### 固定格式

```markdown
- **<结论式纪律，一句话可执行>**（YYYY-MM-DD 实测修复[, 任务#N 复现]）：
  原实现是 <X> → 真实现象是 <Y> → 根因是 <Z> → 修复口径是 <W>。
  **通用纪律：凡<同类场景>一律<正确做法>，禁止<错误做法>**
```

### 真实范例（保持此风格）

```markdown
- **附件角色识别必须「表头特征优先」，文件名关键词只作末级兜底**（2026-10-14 实测修复，任务#4 复现）：
  散装 xlsx 原只做文件名关键词 verbatim 匹配（`"审计规则方法公式" in 文件名`），
  真实业务名是「稽查数据探查规则方法公式（9月）异常统计.xlsx」→ substring 不命中
  → 创建任务回显「④ 附件1审计规则未自动识别」、发起人被迫多一轮人工指认
  （而同一文件 `classify_xlsx_role` 早已判为 `audit_rule`，能力有却未用于散装）。
  修复：`_expand_bind_pool` 把散装 xlsx 与 zip 内层统一进同一角色池。
  **通用纪律：识别「这是什么文件」一律以表头特征为准，文件名关键词（业务专名）
  只作磁盘不可读时的末级兜底，且禁止写成本次出现的完整文件名**
```

### 格式要点

1. **结论前置且加粗**——读者扫一眼就知道该怎么做
2. **必带日期 + 「实测」字样**——区分"推导出来的"和"翻车验证过的"（实证：elink AGENTS.md 27 行含日期戳、16 行含"实测"）
3. **保留现象与根因**——只有结论没有根因，下次换个场景就不会迁移
4. **以「通用纪律」收尾**——从个案抽象到同类场景，这是回写的真正目的

### 唯一真源清单（配套机制）

教训回写到一定数量后，会发现**多数事故源于「同一逻辑存在第二份实现」**。此时应新增独立小节聚合索引：

```markdown
## 唯一真源清单（禁止第二份实现）

> Agent 最常犯的错不是写错逻辑，而是**复制一份逻辑**。改动下列任一主题前，
> 先定位唯一真源并复用；发现第二份实现即视为缺陷。
> 各条目的事故背景与详细口径见本文件对应章节（本表只做索引，不替代原文）。

| 主题 | 唯一真源 | 禁止行为 |
|------|---------|---------|
| <判定/校验/口径> | `<模块>::<函数>()` | <具体的错误做法 + 后果> |
```

> ⚠️ 聚合时**必须保留原条目的事故上下文**（日期 + 现象 + 根因），只加索引表，不删原文。
> 实证：elink-monitor AGENTS.md 中"口径"出现 15 次、"单一真源" 2 次、"禁止写死" 4 次，最终聚合出 18 行唯一真源清单。

### memory 沉淀口径（跨会话）

| category | importance | tier | 用途 |
|----------|-----------|------|------|
| `decision` | 5 | hot | 关键技术决策 + **撤销条件** |
| `lesson` | 4-5 | hot/warm | 新 Bug 模式、兼容性陷阱、第三方依赖风险 |
| `knowledge` | 4 | warm | 新规范、唯一真源、口径约定 |
| `event` | 2-3 | cold/warm | 写后即记（改了什么文件 / 验证结果 / 是否 commit） |
| `task` | 5 | hot | **Handoff**（长任务中断续做，`title="Handoff: ..."`） |

> **未 commit 的改动必须在记忆标题标注「（未commit）」**——这是跨会话 handoff 的关键，否则下个会话会误以为已入库。
